# 查询澄清表单

Query Planner 在缺少必要条件、指代不明确时返回 `needs_clarification=true`、`plan=null` 和非空 `clarify` 列表。`task_action=CONTINUE` 仅表示接续任务，与澄清决策独立。

```json
{
  "in_domain": true,
  "needs_clarification": true,
  "plan": null,
  "reply": null,
  "clarify": [
    {"key": "base", "label": "币种", "type": "text", "reason": "missing", "message": "请填写要查询的币种", "placeholder": "例如 BTC、ETH"},
    {"key": "count", "label": "期数", "type": "number", "reason": "missing", "message": "请填写最近多少期", "hint": "比较最近多少期的平均费率", "min": 1, "max": 100}
  ]
}
```

每项只收一个必要条件，所有展示项必填。模型新输出的 `key/label/type/reason/message` 必填；`placeholder/hint/options/min/max/minSelections/maxSelections/value` 可选。旧字段缺少 reason 时按 missing 兼容。类型为 `text/number/date/select/multiselect`，选择框必须提供非空字符串 `options`，范围只用于数字框。schema 按类型拆分分支：`select` 的 `options` 是 required 且 minItems=1，不仅在描述中声明；完全相同的重复字段由 uniqueItems 约束，key 唯一性仍由服务端校验。列表最多 8 项，key 必须唯一。标签简短，不出现内部字段路径或查询协议名；明确有效的条件不重复问；无效或含糊的已有值可以说明原因后再次询问。上例适用于用户已明确比较最近几期平均费率、但未提供币种和期数的情况。

无需澄清时显式返回 `needs_clarification=false`、`clarify=[]`。明确不支持的查询应说明能力缺口，不能把不支持的口径作为可查询选项。无法一次确定的依赖条件可以在用户选择后继续询问，例如先选择最近一期或最近几期平均，再对后者追问期数。

## 单选与多选

`select` 只选一个值，提交字符串；`multiselect` 使用复选框，提交字符串数组。用户说“两所”仅约束数量为2，不表示已经指定币安和OKX。即使当前目录只有这两所，模型仍可澄清具体对象；用户明确名字时保留已给出的对象。不得编造目录之外的交易所选项。

```json
{
  "key": "exchange", "label": "交易所", "type": "multiselect",
  "reason": "missing", "message": "请选择要比较的两家交易所。",
  "options": ["币安", "OKX"], "minSelections": 2, "maxSelections": 2, "value": []
}
```

`minSelections/maxSelections` 只用于多选，新的模型 schema 要求显式填写；数量未限定时填写1和全部选项数。服务端兼容缺省字段，按1和全部选项数处理。要求恰好N项时两者均为N；范围必须满足 1 ≤ minSelections ≤ maxSelections ≤ 选项数，不使用数值输入的 min/max 表达数量约束。

前端显示已选数量，少选或多选时明确提示并阻止提交；后端同时验证数组结构、去重、数量边界及选项成员身份，不能通过直接请求绕过选择约束。可从三项中选两项，不要求把全部选项都选上。正常提交示例：`clarificationAnswers:{"exchange":["币安","OKX"]}`。

请求、任务快照、SSE 和历史回显均保留数组。用户此前选了一个值而本轮改为多选时，会回显原值并勾选匹配项，不自动补上其余项；不能把数组拼接成一个交易所名称。旧的单值提交与字符串历史快照继续兼容。已有值不在新选项中时仍显示“上次填写”，不自动替换或猜选项。

## 补缺失、纠错与确认

- reason=missing：用户尚未提供该条件。
- reason=invalid：已提供但格式、范围或业务要求不合法。message 必须指出问题和约束，例如“期数需要1～100，您填写的是200”。
- reason=confirm：已提供但含糊、有歧义或需要选择确认。message 必须说明具体歧义或待确认事项。

不按已填写 key 删除模型的澄清项；同一个字段可以合法地再次出现，用于纠错或确认。已收到值不等于值正确。比特币等明确常用名可以归一化为 BTC，不应仅因中文表达重复询问。程序回显当前表单提交的真实原值，不把模型猜测当成用户填写值；普通文本答案也包含 message，旧客户端不会丢失原因。

```json
{
  "key": "count", "label": "期数", "type": "number",
  "reason": "invalid", "message": "期数需要1～100，您填写的是200，请修改。",
  "value": "200", "min": 1, "max": 100
}
```

表单请求示例：`{conversationId, parentTurnId, question, clarificationAnswers:{"count":"10"}}`。没有 clarificationAnswers 的旧客户端继续使用原文字追问接口。

## 接口与接续

- `/api/ask` 响应、`/api/ask/stream` 的 `done` 事件、`/api/conversation/latest` 中的问答记录，均提供顶层 `clarify` 数组；无表单时为 `[]`。
- Query 的结构化结果保存在已有 `agent_payload_json` 中，响应中的 `planning.status` 为 `NEEDS_CLARIFICATION`，`planning.clarify` 为字段列表。不新增数据库字段。
- 普通答案文本包含字段标签和说明，供旧客户端显示，也写入任务的未完成问答链。
- 前端按列表渲染输入框。message 在对应字段旁展示，invalid 为纠错说明、confirm 为确认说明；value 显示为“上次填写”并尽可能预填输入框。选择框的原值不在新选项中时仍保留原值文字，不擅自选择。
- 点击“继续查询”后，同时发送供用户阅读的 question 和 `clarificationAnswers`（key → 用户原值），携带同一 conversationId 和当前 parentTurnId。服务端对照父轮次已展示的表单校验字段身份和请求结构；业务值是否正确仍由规划/编译判断，不能因为已有值就当成已验证。
- 用户原值保存在任务版本的 clarificationAnswers 中，后续表单提交更新同 key 的值并保留其他项；成功执行后由正常查询状态接续。不添加数据库列。下一轮仍经过规划和计划校验，不直接把填写值写入可执行计划。
- 刷新页面恢复表单，只允许当前父轮次的表单提交。提交期间、防重复提交和上下文冲突沿用现有问答约束；历史表单只读，用户仍可在主输入框自由补充。

## 兼容与失败行为

服务端继续接受有文字的旧 `clarify` 字符串，以普通文字显示。有效非空列表即视为澄清，即使模型漏写标志，也不执行附带计划。

`needs_clarification=true` 但列表为空、缺失或字段不合法时，记录 `CLARIFY_INVALID`，同时在服务日志打印 traceId 与具体字段错误，不能标成澄清成功。若 planner 重试预算尚未耗尽，最多进行一次专项表单修复：使用独立的简短提示词、原问题及原任务上下文，不重发完整的查询/计算 schema；配置 json_schema 时，修复契约仅含 `clarify`，明确 `minItems=1`。已正常返回有效列表时不做额外调用。

专项修复仍无有效字段则记录 `REPAIR_EXHAUSTED`，本轮为 FAILED，不取数、不调用答案模型、不返回假的空表单，页面显示“澄清表单生成失败”；即使配置允许更多重试，也不循环修复。专项结果不能切换任务或执行其附带计划。非法列表不部分展示，避免遗漏必要条件。没有澄清标志和有效列表的空计划仍属于无效计划，可按原策略修复。

模型是否提出了正确的业务问题仍取决于模型输出。字段类型、唯一性、长度、选项及范围由服务端校验；条件是否已补齐、计划是否可执行由后续规划与编译校验，表单提交本身不代表查询已成功。
