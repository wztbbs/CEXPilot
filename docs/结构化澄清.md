# 查询澄清表单

Query Planner 在缺少必要条件、指代不明确时返回 `needs_clarification=true`、`plan=null` 和非空 `clarify` 列表。`task_action=CONTINUE` 仅表示接续任务，与澄清决策独立。

```json
{
  "in_domain": true,
  "needs_clarification": true,
  "plan": null,
  "reply": null,
  "clarify": [
    {"key": "base", "label": "币种", "type": "text", "placeholder": "例如 BTC、ETH"},
    {"key": "count", "label": "期数", "type": "number", "hint": "比较最近多少期的平均费率", "min": 1, "max": 100}
  ]
}
```

每项只收一个必要条件，所有展示项必填。`key/label/type` 必填；`placeholder/hint/options/min/max` 可选。类型为 `text/number/date/select`，选择框必须提供非空字符串 `options`，范围只用于数字框。列表最多 8 项，key 必须唯一。标签简短，不出现内部字段路径或查询协议名；已知条件不重复问。上例适用于用户已明确比较最近几期平均费率、但未提供币种和期数的情况。

无需澄清时显式返回 `needs_clarification=false`、`clarify=[]`。明确不支持的查询应说明能力缺口，不能把不支持的口径作为可查询选项。无法一次确定的依赖条件可以在用户选择后继续询问，例如先选择最近一期或最近几期平均，再对后者追问期数。

## 接口与接续

- `/api/ask` 响应、`/api/ask/stream` 的 `done` 事件、`/api/conversation/latest` 中的问答记录，均提供顶层 `clarify` 数组；无表单时为 `[]`。
- Query 的结构化结果保存在已有 `agent_payload_json` 中，响应中的 `planning.status` 为 `NEEDS_CLARIFICATION`，`planning.clarify` 为字段列表。不新增数据库字段。
- 普通答案文本包含字段标签和说明，供旧客户端显示，也写入任务的未完成问答链。
- 前端按列表渲染输入框；点击“继续查询”后，以“补充本轮查询条件”及各标签、值发送同一会话的下一轮请求，携带当前 `parentTurnId`。下一轮仍经过规划和计划校验，不直接把填写值写入可执行计划。
- 刷新页面恢复表单，只允许当前父轮次的表单提交。提交期间、防重复提交和上下文冲突沿用现有问答约束；历史表单只读，用户仍可在主输入框自由补充。

## 兼容与失败行为

服务端继续接受有文字的旧 `clarify` 字符串，以普通文字显示。有效非空列表即视为澄清，即使模型漏写标志，也不执行附带计划。

`needs_clarification=true` 但列表为空、缺失或字段不合法时，记录 `CLARIFY_INVALID`，不能标成澄清成功。若 planner 重试预算尚未耗尽，最多进行一次专项表单修复：使用独立的简短提示词、原问题及原任务上下文，不重发完整的查询/计算 schema；配置 json_schema 时，修复契约仅含 `clarify`，明确 `minItems=1`。已正常返回有效列表时不做额外调用。

专项修复仍无有效字段则记录 `REPAIR_EXHAUSTED`，本轮为 FAILED，不取数、不生成答案、不返回假的空表单；即使配置允许更多重试，也不循环修复。专项结果不能切换任务或执行其附带计划。非法列表不部分展示，避免遗漏必要条件。没有澄清标志和有效列表的空计划仍属于无效计划，可按原策略修复。

模型是否提出了正确的业务问题仍取决于模型输出。字段类型、唯一性、长度、选项及范围由服务端校验；条件是否已补齐、计划是否可执行由后续规划与编译校验，表单提交本身不代表查询已成功。
