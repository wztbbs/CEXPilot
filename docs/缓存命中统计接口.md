# 缓存命中统计接口

```text
GET /api/stats/cache?startTime=<Unix毫秒时间戳>&endTime=<Unix毫秒时间戳>
```

只有两个参数：startTime 必传，endTime 可选，省略时取应用服务器当前时间（Clock）。接口按 `[startTime,endTime)` 选择 `ask_trace.created_at`，相邻窗口不重复计算边界记录。时间戳不带时区，统一表示绝对时刻；不是 Unix 秒，也不是日期字符串。开始必须早于结束。

新接口直接在现有 ask_trace 和 trace_event 上聚合，不新增表或字段，不请求模型或交易所。FROM_UNIXTIME 在数据库会话时区转换边界，保持与 created_at 写入时使用的 NOW() 相同的时区口径；当前 created_at 为秒精度，毫秒边界向上取整后比较，保持原范围语义。

返回示例（演示数据）：

```json
{
  "startTime": 1793318400000,
  "endTime": 1793336400000,
  "promptTokens": 100000,
  "cachedTokens": 95000,
  "cacheHitPercent": 95.00,
  "measuredCalls": 3,
  "unknownCalls": 0,
  "stages": {
    "route": {
      "promptTokens": 1000,
      "cachedTokens": 0,
      "cacheHitPercent": 0.00,
      "measuredCalls": 1,
      "unknownCalls": 0
    },
    "plan": {
      "promptTokens": 98000,
      "cachedTokens": 95000,
      "cacheHitPercent": 96.94,
      "measuredCalls": 1,
      "unknownCalls": 0
    },
    "answer": {
      "promptTokens": 1000,
      "cachedTokens": 0,
      "cacheHitPercent": 0.00,
      "measuredCalls": 1,
      "unknownCalls": 0
    },
    "other": {
      "promptTokens": 0,
      "cachedTokens": 0,
      "cacheHitPercent": null,
      "measuredCalls": 0,
      "unknownCalls": 0
    }
  }
}
```

- 比例为有效 LLM 调用的缓存 token 总和 / 输入 token 总和 × 100，保留两位小数。不是逐次调用命中率的平均值，不包含输出 token。
- measuredCalls 是参与计算的 LLM 调用数，一个 ask 可以包含多次调用，包括路由、规划、回答、修复重试。
- 有效调用要求 prompt_tokens > 0，且 0 ≤ cached_tokens ≤ prompt_tokens。cached_tokens=0 正常计入；缺失或异常用量计入 unknownCalls，分子分母同时排除。
- 未知统计、全部无效或没有调用时，promptTokens/cachedTokens/measuredCalls 为零，cacheHitPercent 为 null，unknownCalls 反映已记录但不可统计的调用。
- 包含用户、脚本及来源未知流量，不按 ask 最终状态筛选。失败 ask 已取得的有效用量也计入；只统计 LLM_CALL，不统计工具事件。
- 时间范围选择的是 ask，而不是 LLM 事件的发生时间。范围内创建的 ask 后续完成的调用也属于该 ask；仍在执行的 ask 之后会继续新增用量，因此重复查询可能增长。
- 只反映已落库的数据；未生成 trace 的拒绝请求、事件落库失败或仍未记录的调用无法从此接口统计。

阶段统计使用同一时间窗口和有效用量规则，各项含义如下：

| 字段 | 含义 |
| --- | --- |
| `promptTokens` | 参与缓存统计的输入 token 总数（分母），不是输入加输出的总和 |
| `cachedTokens` | 这些输入中命中的缓存 token 总数（分子） |
| `cacheHitPercent` | 本阶段 cachedTokens / promptTokens × 100；没有有效输入时为 null |
| `measuredCalls` | 本阶段有有效缓存统计的调用次数，包含重试 |
| `unknownCalls` | 本阶段已记录但缓存用量缺失或不合法的调用次数 |

按 `trace_event.name` 归类，只处理 `event_type='LLM_CALL'`：

| 输出阶段 | 调用名 |
| --- | --- |
| `route` | `router`；兼容 `intent_router`、`route` |
| `plan` | `dag_planner`、`monitor_planner`、`clarification_repair`；兼容 `planner`、`plan` |
| `answer` | `answer` |
| `other` | 空名称、未识别的历史名称或未来新阶段 |

`stages` 固定返回四项；某阶段没有调用时计数为 0、命中率为 null。未知阶段仍计入 other 和整体汇总，避免漏掉用量。监控规划与查询规划合并到 plan，澄清修复与规划重试同样计入 plan。

顶层字段保留原有整体统计，现有回归脚本无需改动即可继续读取。整体值直接由同一次 SQL 聚合的各阶段加总，避免运行中的 ask 新增用量导致总分不一致；整体命中率仍按 token 加权，不能把各阶段百分比直接平均。上述示例整体达到 95%，但 route 与 answer 均为 0%，可暴露规划输入占比过大所掩盖的问题。

直调 LLM 的 `replay_trace.py` 不生成线上 ask_trace/trace_event，因此其消耗不进入本接口。固定问答没有 LLM_CALL，也不计入调用分母。无需新增表、字段或回填历史数据，不读取完整 prompt/response JSON。

返回 HTTP 400：缺少 startTime、参数不是整数、时间戳为负、超过数据库支持范围，或开始不早于结束。没有数据正常返回 HTTP 200。接口设置 Cache-Control: no-store。

本地测试使用 H2 MySQL 模式与固定 Clock，覆盖范围边界、跨时段调用、零命中/缺失/非法用量、失败 ask、默认结束时间、按 token 总量加权、阶段映射、监控/重试归属、未知名称归 other、空阶段及整体与分阶段一致性，不调用线上接口。
